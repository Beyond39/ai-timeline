# AI Conversation Visual Navigator：现有代码评估与插件迁移建议

日期：2026-10-02  
目标形态：Chrome 浏览器插件，兼顾后续 Edge 适配。  
依据：用户提供的项目设想、当前工作区源码，以及浏览器扩展和 OpenAI 官方文档。  
评估方式：静态阅读源码与数据结构。本次没有运行功能测试、启动现有应用、调用模型、抓取真实 ChatGPT 页面，也没有修改现有业务代码。运行效果与当前页面适配情况留给用户实际体验确认。

## 1. 结论与这次调整

现有代码值得保留。最有价值的是原始来源归档、消息与证据关联、导入预览、Q/A 映射、连续片段分组、缓存及人工修订规则。这些工作已经为“能读原文、能定位来源”的产品打下基础。

产品入口和运行方式需要调整。现有界面围绕 Topic Tree、摘要和知识整理展开，新插件应围绕项目中的完整对话、每轮 Q/A 和连续讨论片段展开。用户随时在 ChatGPT 页面保存当前讨论，再在插件侧栏阅读问答，在插件完整页面浏览项目地图。

此前指导书建议先做本地 Python 应用，再接浏览器插件。按照这次明确的选择，实施优先级更新为：**插件是主产品，浏览器内本地存储是第一版基础；现有 Python 实现作为迁移参考和可选的后续处理引擎。** 首版不以启动 Python 服务为前提。

这不是把旧界面装进插件弹窗就完成了。Python 代码不能直接在普通浏览器插件中运行；核心规则需要迁移到 JavaScript/TypeScript，SQLite 数据结构需要转为适合插件的存储结构。旧代码保留为参考，减少重复设计和追溯能力的损失。

## 2. 插件读取 ChatGPT 内容的范围

### 2.1 为什么插件方向合适

浏览器扩展的 content script 能读取其获准访问页面的 DOM，并将采集结果传给扩展。因此，对“正在打开的 ChatGPT 对话”而言，插件确实更贴近使用现场，能够减少下载文件、选择文件和重复导入的操作。[Chrome content scripts 官方文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

适合的基本流程是：打开对话 → 点击插件 → 预览本次识别出的消息 → 选择归属项目 → 保存 → 展开 Q/A → 回到原页面或插件中的原文位置。

### 2.2 不能直接推出的能力

页面读取能力不等于已经取得整个账户、所有项目、全部历史分支与附件的读取能力。未进入当前页面的数据、尚未加载的旧消息、没有展示的分支，以及没有提供正文的附件，需要各自的获取路径。

这里是能力边界判断，**并非对当前 ChatGPT 页面实现的现场检查结论**。当前 DOM、滚动加载方式、消息标识以及项目标识的可见情况仍需在开发采集器时确认。

使用 `activeTab` 可在用户主动点击插件后取得当前标签页的临时访问权限；它不是账户历史授权。第一版可以按用户主动采集设计，需要持续自动捕获时再增加明确的站点访问权限。[Chrome activeTab 官方文档](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

另外，模型使用、登录授权和聊天历史读取是不同能力。OpenAI 的 Sign in with ChatGPT 官方说明明确指出，使用相应计划不会让应用获得 ChatGPT 对话和记忆。因此，不能把登录或调用模型当成聊天记录导入接口。[OpenAI Sign in with ChatGPT 文档](https://learn.chatgpt.com/docs/sign-in-with-chatgpt)

### 2.3 建议保留三种输入方式

| 方式 | 用户场景 | 第一版处理规则 |
|---|---|---|
| 当前页面采集 | 保存刚发生的讨论，随手进入阅读器 | 标明采集范围、消息数和采集时间；只承诺实际获取到的内容 |
| 多对话归入项目 | 把不同聊天整理为同一个长期项目 | 用户选择归属；保留每条对话的独立身份和来源 |
| 导出文件导入 | 回填过去的长期对话，批量建立地图 | 延续现有 ChatGPT JSON 和通用 JSON 的解析思路，先预览再保存 |

插件中的“本地项目”与 ChatGPT 原生项目需要区分。原生项目标识能够可靠识别时，可保存其来源和识别方式；无法确认时，允许用户手动归属。不能仅凭对话标题、导入文件名或一次页面路径猜出原生项目关系。

## 3. 现有代码到底有多少可以用

### 3.1 实际实现规模

按 `ai_memory/` 内 `.py`、`.js`、`.css`、`.html` 源文件的非空行统计，包含注释与文档字符串，排除缓存、测试、输出文件和其他目录的占位说明：

| 范围 | 文件数 | 非空行数 |
|---|---:|---:|
| Python 源文件 | 31 | 3,727 |
| 当前前端 HTML / CSS / JS | 3 | 571 |
| 合计 | 34 | 4,298 |

约 87% 的上述非空行来自 Python。这只说明当前技术构成，**不是完成度，也不是可复用率**。不能据此声称“87% 可以直接搬到插件”，也不能根据行数估算剩余工期。

实际业务实现集中在 `ai_memory/`。`apps/web`、`apps/api` 和多个 `packages/` 子目录主要是未来边界的 README；Agent 目录主要是待实现的骨架。当前没有发现浏览器插件的 `manifest.json`。因此，迁移需要建立真实的扩展入口，但不需要拆除一个已完成的大型 SaaS 系统。

### 3.2 复用判断

| 当前部分 | 判断 | 插件中的处理方式 |
|---|---|---|
| ChatGPT / 通用 JSON 导入 | 高价值，迁移规则 | 转为 JS/TS 解析器；保留导入预览，增加分支路径与内容类型处理 |
| 原始文件、来源版本、消息、证据 | 高价值，迁移数据设计 | 原文与采集快照分层存储；保留来源关联，使用扩展内 IndexedDB |
| Q/A 管线 | 有用，但需要修改核心边界 | 保留全文与索引思路；支持未回答问题、回答组、分支及原始顺序 |
| Fragment 分段 | 最接近新产品核心 | 迁移按轮次分块与相邻讨论合并规则，升级为可编辑 Segment |
| Topic、别名、人工覆盖 | 保留规则，调整角色 | Topic 作为标签与筛选维度；人工修订优先于自动分析 |
| 当前前端 | 部分直接复用 | 可复用转义、交互样式与全文定位思路；重做主导航与存储接入 |
| 彩色界面原型 | 可复用视觉与交互设计 | 保留色彩、视图切换、展开阅读；替换示例数据与宿主专用接口 |
| 缓存、证据校验、修订记录 | 高价值，迁移规则 | 增量分析、版本校验、撤销与重算保护继续使用这些原则 |
| Python API / CLI / SQLite 运行层 | 延后作为可选工具 | 首版插件不依赖本地服务；可用于后续大型批处理或兼容旧项目 |
| 知识 Markdown 编译、AI 延展、Agent 骨架 | 延后 | 先完成对话读取与导航，再判断是否需要知识输出和自动代理 |

“复用设计”与“直接运行原代码”应分开理解。迁移到纯插件时，源数据模型和算法思路的保留价值很高；Python 的直接运行价值取决于是否保留额外运行环境。当前前端和原型在浏览器里更容易复用，但也需要解除对旧 API 和宿主接口的依赖。

## 4. 与源码对应的关键发现

### 4.1 已有完整原文基础，主界面没有把它放在中心

`service.py` 的 `get_message()` 会返回完整消息及来源信息，`conversation_messages()` 按消息序号返回整段对话。`app.js` 的证据点击流程已经能加载完整对话、显示全文并突出选中消息。因此，现有工程并非只有摘要。

但是，首页里的 Q/A 与时间线区域带有 `hidden`；辅助请求只取 20 条 Q/A 和 30 条时间线事件，没有加载更多入口。Topic 详情中的 Q/A 卡片显示的是摘要，Topic 查询还限制为最多 100 条。对长期项目阅读来说，这些入口和数量限制不够。

迁移时应让“完整对话阅读器”和“Q/A 索引”成为独立主界面，摘要只负责帮助定位。全文保留、连续阅读与加载更多不应依赖地图分析是否完成。

依据：[全文消息接口](D:/mytools/GPT-SaaS/ai_memory/service.py:409)、[证据面板的原文读取](D:/mytools/GPT-SaaS/ai_memory/static/app.js:102)、[隐藏的问答区域](D:/mytools/GPT-SaaS/ai_memory/static/index.html:85)、[有限数量的辅助请求](D:/mytools/GPT-SaaS/ai_memory/static/app.js:112)、[Topic 详情的 Q/A 查询](D:/mytools/GPT-SaaS/ai_memory/tree.py:329)。

### 4.2 Q/A 不能继续只表示“一个问题加一条回答”

当前导入会记录每条用户消息为 question，这有价值；`list_questions()` 也能返回未回答问题。但 Q/A 管线通过 `JOIN question_answers` 读取已配对的问答，未回答问题不会进入 `qa_units`。这两个层面的行为需要区分，不能笼统地说“问题完全丢失”。

导入时只关联“直接父消息为 user 的 assistant 消息”。这不足以表达继续生成、多条回答、中间经过工具消息的回答，以及重新生成的不同分支。数据库的 `qa_units` 又要求单个 `answer_message_id`。

建议把 Q/A 定义成可阅读的一轮讨论：

- 一条用户消息作为起点。
- 当前选定分支上、下一个用户消息之前的相关回答组成回答组。
- 工具事件可以折叠，但保留身份、顺序与来源。
- 没有回答时仍显示这一轮，状态为“未回答”。
- 重新生成或编辑形成的其他路径作为版本或分支处理，避免混进同一条线性回答。

依据：[当前问答内连接](D:/mytools/GPT-SaaS/ai_memory/qa.py:183)、[导入时的父消息配对](D:/mytools/GPT-SaaS/ai_memory/service.py:324)、[单回答 Q/A 表](D:/mytools/GPT-SaaS/ai_memory/database.py:168)。

### 4.3 语义编译与 Q/A 生成当前可能脱节

`ProjectTree.compile()` 在提取器带有 `provider` 属性时传入 `analyze_qa=False`，`KnowledgeCompiler.compile()` 仅在该参数为真时运行 `QAPipeline.analyze()`。从这条调用链看，单独走语义编译的项目可能生成片段与主题，却没有生成 Q/A 单元；此前已生成 Q/A 的情况则不同。

这是一项静态调用链发现，没有执行运行验证。插件版应在采集或导入完成后独立生成问答索引，地图与模型分析使用同一份索引，不控制问答是否存在。

依据：[语义流程的参数](D:/mytools/GPT-SaaS/ai_memory/tree.py:46)、[Q/A 生成条件](D:/mytools/GPT-SaaS/ai_memory/compiler.py:47)。

### 4.4 导出解析保留了父子关系，却没有恢复当前阅读路径

ChatGPT 解析器保存 `parent_external_id`，这是好的基础；但它把 mapping 中提取的所有文本消息按时间和 ID 排序，没有利用当前节点确定当前分支路径。编辑问题、重新生成回答等情况可能存在多个路径，直接按时间平铺不能确保还原一次连续讨论。

新的导出解析器需要先保存节点图，再明确当前阅读路径。文件提供可靠的当前节点信息时据此恢复；缺少相关信息时标记不确定并允许用户选择，避免猜测成事实。

页面采集只能保存实际取得的当前内容。未展示的其他分支需要导出数据或其他明确获取方式，不能由当前 DOM 自动补出。

依据：[ChatGPT 导出解析器](D:/mytools/GPT-SaaS/ai_memory/connectors/chatgpt.py:25)、[消息平铺排序](D:/mytools/GPT-SaaS/ai_memory/connectors/chatgpt.py:80)。

### 4.5 增量保存需要更稳定的身份

现有导入以 `external_project_id` 或 `source_path` 推导项目，上传预览的路径可能带有临时标识。对话内部 ID 又包含整份源文件的哈希。只要整个导出文件内容发生变化，即便某条对话没改，其版本身份也会随之变化。

这对“完整源文件版本归档”有意义，但不适合直接作为浏览器日常增量采集的逻辑身份。新的规则应分开保存：

- 项目身份：稳定的本地项目 ID，以及可选的原生项目关联。
- 对话身份：可靠的源对话标识；没有时保留来源地址及低置信度回退身份。
- 消息身份：可靠的源消息 ID 优先；回退匹配记录依据和不确定性。
- 采集快照：本次时间、采集范围与内容哈希。
- 消息版本：同一逻辑消息修改后的正文版本。

不能因为一次采集没有看到旧消息，就把旧消息从本地删除；“未采集到”与“源消息已删除”是不同事实。不能单凭内容哈希合并所有消息，因为不同轮次可能出现相同内容。

依据：[项目身份生成](D:/mytools/GPT-SaaS/ai_memory/service.py:224)、[含文件哈希的对话身份](D:/mytools/GPT-SaaS/ai_memory/service.py:262)。

### 4.6 非文本内容与时间需要明确表达

ChatGPT 解析器会跳过提取后没有文本的消息。服务会另外归档输入原始字节，因此不能说原始输入已不可恢复；但是这些消息没有进入常规消息阅读列表。插件需要保留附件、图片或其他内容的存在、类型与能取得的描述。没有附件正文时显示该状态，不把它伪装成已完整保存。

当前 timeline 使用消息来源时间，这是值得保留的做法。新插件还需区分来源时间、采集时间和分析时间：页面未提供可靠来源时间时使用未知值，并标明时间精度，不能把今天保存的旧对话画成今天发生的讨论。

依据：[跳过无文本消息](D:/mytools/GPT-SaaS/ai_memory/connectors/chatgpt.py:61)、[原始来源版本](D:/mytools/GPT-SaaS/ai_memory/database.py:238)、[基于消息时间的 timeline](D:/mytools/GPT-SaaS/ai_memory/experience.py:58)。

### 4.7 Fragment 已接近 Segment，不能直接等同

`FragmentService.segment()` 按用户轮次切块；`semantic_segment()` 为这些轮次标注主题，再合并相邻同主题轮次，并继承原始证据。这是本次转向中最值得保留的核心实现。

但现有 Fragment 主要记录序号区间和证据关联，尚未建立新产品需要的明确 Q/A 成员关系、人工拆分合并、稳定的边界修订与撤销规则。人工 Topic 覆盖已存在，但不等于人工 Segment 边界编辑。

另外，语义分段每批 16 个轮次，只发送每轮前 1,600 字符进行主题判断。原文存储没有因此截断，但长回答后部的转折可能不参与边界判断。迁移时应保留可复核边界与人工纠正能力，按需改进长文本分析与跨批主题一致性。

依据：[Fragment 与语义合并](D:/mytools/GPT-SaaS/ai_memory/fragments.py:86)、[截取主题判断输入](D:/mytools/GPT-SaaS/ai_memory/fragments.py:110)、[人工主题覆盖](D:/mytools/GPT-SaaS/ai_memory/tree.py:221)。

### 4.8 当前 Topic Tree 可以支持分类，思想演进关系要另外建模

当前 Topic Tree 的节点与父子关系适合主题归类。项目中“一个想法促成了哪个决定”“这一段推翻了前一段什么假设”等关系，需要独立的 Segment 关系边及来源证据。

第一版地图先展示真实顺序与归属。后续再加入“延续、分支、替代、引用”等关系；模型推断的关系应标明是建议，并能由用户修改。不能把 Topic 的分类父子关系直接解释为讨论的因果关系。

### 4.9 旧 API 不能直接视作插件桥接接口

现有服务的 POST 请求会检查 Origin，浏览器扩展来源不在当前允许的同源范围内。即便后续保留本地 Python 引擎，也需要专门设计扩展配对、来源允许范围和访问凭据，并处理跨域与服务生命周期。

因此，首版优先纯插件存储和处理；如确有大型批处理需求，再添加可选桥接。当前 Python 服务继续保留，便于参考和旧数据处理。

依据：[现有 Origin 检查](D:/mytools/GPT-SaaS/ai_memory/api.py:134)。

## 5. 新插件的数据骨架

阅读层级建议为：**项目 → 对话 → Segment → Q/A 轮次 → 原始消息**。Topic 是可多选的标签与颜色维度，可以贯穿多条对话和多个 Segment。

| 对象 | 最少字段与关系 | 设计要求 |
|---|---|---|
| Project | 本地 ID、名称、颜色、可选原生项目标识及其来源 | 手工归属可用；自动识别须记录依据 |
| Conversation | 本地 ID、源 ID、项目、标题、来源地址、分支状态 | 逻辑身份不随整份导出文件哈希变化 |
| Message | 源消息 ID、角色、正文、内容类型、父节点、路径顺序、时间及精度 | 原文与归档版本保留；无法取得正文时标明 |
| CaptureSnapshot | 对话、采集时间、采集方式、范围、内容哈希、完成状态 | 区分当前可见内容、导入数据与未知覆盖范围 |
| Turn / QA | 起始用户消息、回答消息组、工具消息引用、路径、状态、顺序 | 未回答问题仍可阅读；摘要不是正文 |
| Segment | 对话、路径、标题、明确成员、主题标签、边界来源、修订版本 | 初始可一轮一段；支持连续讨论合并 |
| SegmentMember | Segment ID、QA ID、成员顺序 | 地图节点展开后直接得到真实成员，避免靠标题重新搜索 |
| Topic | ID、项目范围、名称、颜色、别名 | 同名主题是否跨项目共享应成为明确产品规则 |
| EvidenceRef | 对话、消息、正文版本、可选文本定位 | 证据指向实际保存的原文与版本 |
| EditRevision | 对象、操作、修改前后、时间、人工/自动来源 | 保护人工边界、支持撤销及重算后恢复 |

移植句子定位时还需注意：Python 的字符串索引与 JavaScript 的 UTF-16 索引对部分 emoji、扩展 Unicode 字符的计数不同。不能把旧字符偏移直接当成新页面高亮偏移；应定义一致的定位约定或重新生成偏移。

首版把本地项目作为主要组织层级，原生项目关系作为可选来源属性。这样能先支持用户已有的多对话项目，又不会把采集器是否能识别某种页面信息变成整个产品的前置条件。

## 6. 插件结构与运行方式

建议使用 Manifest V3，结构分为四个职责：

1. **页面采集器**：识别对话与消息，保留角色、顺序、内容类型、可取得的来源标识；返回范围与识别结果。页面选择器集中在 ChatGPT 适配器中。
2. **扩展消息与保存层**：接收采集结果、验证结构、管理 IndexedDB、生成 Q/A 索引、处理增量合并。必要状态落盘，任务不依赖某个弹窗一直打开。
3. **侧栏阅读器**：显示当前对话、采集预览、Q/A 索引、全文和项目归属，适合边聊边读。
4. **插件完整页面**：显示整个项目、对话列表、彩色地图、搜索筛选及更大空间的全文阅读。

Chrome 官方 Side Panel API 支持用扩展本地 HTML 提供侧栏，适合作为持续阅读入口；具体浏览器版本与 Edge 兼容情况在交付包中声明并由用户体验确认。[Chrome Side Panel 官方文档](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)

### 6.1 存储位置

对话原文、快照、问答索引、Segment 与修订记录放在**扩展自己的 IndexedDB**。小规模设置可使用扩展设置存储。提供项目导出、备份和删除入口。

Content script 直接访问的网页存储属于宿主网站来源，不等于扩展自己的存储。因此，采集器应通过扩展消息传递提交结果，由扩展来源的页面或后台保存。扩展来源的 IndexedDB 可以由相应扩展页面与后台访问。[Chrome 存储与来源隔离文档](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies)

浏览器内持久化不是永久归档承诺。明确提供备份导出，不依赖“数据永远不会被清理”的假设。

### 6.2 旧彩色原型的移植

现有可交互原型可以保留颜色、视图布局、筛选、节点展开和 Q/A 阅读设计，但目前使用示例数据。接入插件时需要：

- 将示例数据替换为统一的数据读取接口。
- 将宿主专用的状态保存接口替换为扩展本地存储。
- 将脚本移到打包内的独立文件，移除依赖外部运行环境的加载方式。
- 地图与阅读器都使用真实对象 ID，共享选中状态。

Chrome 扩展页面默认 CSP 限制脚本来源，并禁止直接执行内联 JavaScript。现有原型不能作为单文件直接装入扩展继续运行，需要进行资源拆分和打包。[Chrome 扩展 CSP 官方文档](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy)

## 7. 界面与颜色：先保证读得到，再保证看得清

### 7.1 侧栏

侧栏顶端显示当前对话与项目归属；旁边提供保存或更新按钮。下面是连续的 Q/A 索引，每一轮都有原始序号、问题开头、回答状态和所属 Segment。

点击一轮后展开完整问题与回答组，支持上一轮、下一轮、只看问题、展开所有回答、回到原文位置。长回答可以收起，但完整内容随时可以打开。工具消息与附件信息作为可展开条目保留。

页面跳转只能使用实际保存的来源地址。页面内精确消息定位有可靠锚点时使用；无法保证时先打开对应对话并说明定位状态，不拼出不存在的深链接。插件自己的阅读器可以根据保存的消息 ID 精确定位。

### 7.2 项目完整页面

建议采用左侧项目/对话导航、中间地图、右侧阅读器：

- 左侧：项目、对话数量、数据来源和采集范围。
- 中间：按时间或路径排序的 Segment，节点标出 Q/A 数、主题与状态。
- 右侧：选中 Segment 的完整 Q/A；进一步可展开所在对话。

地图选中节点后，侧栏与阅读器同步选中真实 Segment 和 QA。搜索原文也直接定位到对应消息，不把用户停留在一个只有摘要的搜索结果里。

### 7.3 颜色规则

继续使用已展示原型的主题颜色：产品蓝、记忆紫、界面青、工程橙、研究绿、Agent 粉。主题色表达讨论内容；选中态使用边框或强调线；未回答、采集范围不完整等状态另配文字与图标。

同一主题在地图、筛选器和 Q/A 条目保持同色。多主题 Segment 可以显示主色与标签，不为每个 Q/A 随机生成颜色。颜色之外仍显示主题名称和状态，避免只能凭颜色理解内容。

## 8. 第一个真正可用的开发切口

### 阶段一：安装、保存与完整阅读

第一份交给用户体验的包应是可以安装的插件，完成一条真实闭环：

**打开一条 ChatGPT 对话 → 点击插件 → 看到采集预览与范围 → 选择项目 → 保存 → 按原顺序展开全部已保存 Q/A → 阅读完整对话 → 刷新后仍能读取。**

这一阶段的必要内容：

- Manifest、侧栏、项目完整页面入口。
- 当前页面采集适配器，识别不确定或内容不足时显示状态。
- 扩展内本地保存与稳定的逻辑身份。
- 用户轮次与回答组索引，包含未回答问题。
- 项目/对话切换、上一轮下一轮、全文阅读和本地原文定位。
- JSON 导入预览，用于回填历史与在页面采集不足时继续使用。
- 项目备份导出和本地数据管理。

不要求模型分析成功才允许阅读。流式回答尚在变化时保留“生成中/待更新”状态；等待可确认的完成状态后提交正式版本，无法可靠判断时允许用户手动更新。

### 阶段二：同一份真实数据上的彩色地图

- 先用用户轮次生成初始 Segment，并允许手工合并相邻轮次。
- 增加时间/主题筛选，显示成员数量。
- 地图与 Q/A 阅读器双向定位。
- 加入边界拆分合并、重命名、Topic 调整和撤销记录。
- Snake、Tree、Story 视图按需要逐步增加，共享同一数据骨架。

第一版 Tree 优先表达归属与已明确的关系。思想演进或因果关系应有证据或人工确认，不能用分类层级替代。

### 阶段三：模型辅助与更大范围整理

- 借鉴现有 semantic segment、缓存和证据验证，生成边界与标题建议。
- 改进长文本、跨批主题一致性和人工边界保护。
- 根据实际需求增加多对话整理、可选本地引擎、可选云同步。
- 再评估知识 Markdown、AI 延展或 Agent 自动整理是否有必要。

云同步和账户体系没有被列为前两阶段的前提。首版的价值是让用户自己的对话变得可读、可浏览、可回溯。

## 9. 用户体验时优先关注什么

遵循“不由助手运行功能测试，直接交给用户体验”的要求，本次没有执行以下操作。这些条目用于下一份插件包的简短体验说明：

1. 当前采集是否准确显示消息数量与范围，能否看到完整长回答。
2. 没有回答的问题、继续生成和工具消息是否按真实路径显示。
3. 同一对话保存两次是否仍是一条对话，并正确保留更新。
4. 不同对话归入同一项目后，切换与搜索是否能找回原文。
5. 地图展开出来的 Q/A 是否正是该 Segment 的成员。
6. 重新打开浏览器后能否读取已保存内容，导出文件能否用于备份。

页面采集范围、源标识可用性和 Edge 兼容性是需要在实际浏览器确认的事项。静态审查只能确定当前代码怎样组织这些能力，不能替代真实页面体验。

## 10. 建议的开工顺序与保留资产

先建立扩展的入口、统一数据模型和本地保存，再迁移 `connectors → 消息路径 → Q/A`。让首份插件包完成真实对话的保存和连续阅读。随后迁移 `fragments → Segment → 地图联动`。最后接回语义标注、缓存、人工修订和可选知识输出。

现有 `ai_memory/` 保留，用于参考导入规则、原文证据关系和增量分析；不急于删除或大幅搬动。当前示例、schema 与指导书继续作为设计资料，但数据结构与实施顺序以本说明中的插件方向为准。
