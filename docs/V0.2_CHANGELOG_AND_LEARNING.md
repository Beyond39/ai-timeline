# AI Project Memory V0.2 开发变更与学习指南

版本：0.2.0
日期：2026-09-13
阶段：可追溯知识编译 Alpha

## 1. V0.2 最终交付结果

V0.2 已经从“能够保存和搜索聊天”推进到“能够把混杂聊天编译成知识文件”。程序会读取 V0.1 保存的句子，将跨对话内容归入同一主题，为每个主题生成独立 Markdown 目录，并保存证据、内容修订和人工审核状态。

示例“学习”项目共有 8 个原句。V0.2 离线编译后形成 5 个主题、16 条主题与证据关系、5 份知识文件。其中“学习方法”收集了来自“学习方法”和“学习规划”两条不同对话的 6 条证据，证明主题不再受原始对话标题限制。

| 指标 | 实际结果 | 含义 |
|---|---:|---|
| 输入句子 | 8 | 来自 2 条混杂对话 |
| 生成主题 | 5 | 学习方法、学习规划、专业课学习、英语学习、高等数学 |
| 主题-证据关系 | 16 | 同一句话允许支持多个主题 |
| 知识文件 | 5 | 每个主题都有独立目录和 README |
| 自动测试 | 9/9 通过 | V0.1 能力保持，V0.2 新能力有回归验证 |
| 实际 API 联调 | 通过 | 5 个主题、5 个文件、“学习方法”6 条证据、1 个修订 |

## 2. 产品结构发生了什么变化

V0.1 的权威对象是项目、对话、消息与句子；V0.2 在上面增加了主题、证据关系、知识文件、修订和审核事件。原始消息仍然不可被摘要覆盖，知识文件只是对事实层的可读投影。

系统现在同时维护三层：事实层保存原文；编译层保存主题与证据关系；知识层生成面向阅读的文件。任何 AI 摘要都必须先经过编译层，不能直接写成“事实”。

| 层级 | 核心对象 | 责任 |
|---|---|---|
| 事实层 | Project / Conversation / Message / Sentence | 保存用户授权导入的原文和位置 |
| 编译层 | CompilerRun / Topic / TopicEvidence | 记录谁在什么时候用什么提取器组织了哪些证据 |
| 知识层 | KnowledgeDocument / Revision / ReviewEvent | 生成文件、保存版本并记录人工判断 |

这个边界保证未来换成 Claude、Gemini、本地模型或新的 OpenAI 模型时，事实层和知识文件结构不需要重写，只替换提取器即可。

## 4. 数据库新增结构

| 表 | 保存什么 | 为什么需要 |
|---|---|---|
| `compiler_runs` | 范围、提取器、模型、来源指纹、运行状态 | 能知道一次知识生成是怎样发生的 |
| `topics` | 稳定主题、摘要、AI 扩展、状态 | 让主题脱离单条对话存在 |
| `topic_evidence` | 主题与句子的多对多关系 | 一句话可以同时属于多个知识主题 |
| `knowledge_documents` | 文件路径、当前修订、审核状态 | 把数据库主题映射为正常文件结构 |
| `document_revisions` | 内容哈希、不可覆盖的历史版本 | 新对话改变知识时保留演化过程 |
| `review_events` | approve/reject/reset 及备注 | 区分模型生成与人的最终判断 |

数据库启动时使用 `CREATE TABLE IF NOT EXISTS` 完成兼容升级，并把 `schema_version` 更新为 2。V0.1 数据无需导出重建。

## 5. 一次知识编译怎样工作

第一步，从数据库读取选定范围的每个句子，同时带上项目、对话、消息、角色和字符位置。第二步，对句子 ID 与正文计算来源指纹。若指纹、提取器、模型和输出位置均未变化，返回 `skipped`。第三步，提取器返回主题、摘要、AI 扩展和证据 ID。第四步，程序验证证据 ID 必须来自本次输入。第五步，保存主题与证据关系。第六步，生成 Markdown 文件并计算内容哈希。只有内容变化时才增加修订。第七步，新修订一律进入 `needs_review`。

`--force` 只表示重新执行提取器，不表示强制制造新版本。如果结果内容相同，修订号保持不变。这避免了“每点一次按钮就产生无意义历史”的问题。

## 6. 生成出来的文件结构

```text
output/knowledge/
├── README.md
├── 专业课学习/README.md
├── 学习方法/README.md
├── 学习规划/README.md
├── 英语学习/README.md
└── 高等数学/README.md
```

知识目录列出主题、审核状态、证据数量、当前修订号和文件链接。每个主题文件把“助手回答形成的核心内容”和“用户提出的相关问题”分开，防止把问题误当结论。

主题文件还包含独立的“AI 扩展（非原始证据）”区域。任何模型补充内容即使看起来正确，也不会与来源归纳混在一起。最后的证据章节记录 `sentence_id`、`message_id`、项目、对话、角色和字符位置，可以回到 V0.1 原文。

## 7. 默认离线提取与可选 LLM

默认 `heuristic-v0.2` 使用明确关键词规则。它的目的不是冒充通用语义理解，而是以零成本和零外传方式证明整个知识编译系统确实可运行。修改规则后再次编译，可以观察知识结构如何变化。

可选 `openai` 提取器通过 Responses API 请求结构化 JSON。请求明确设置 `store: false`，使用 `text.format.type = json_schema`，并要求用户显式填写模型 ID。程序不保存 API Key，只从 `OPENAI_API_KEY` 环境变量读取。

OpenAI 官方 API 文档说明，Responses API 接收文本等输入并生成文本或 JSON；`instructions` 可作为系统级指令；结构化输出可通过 JSON Schema 配置。V0.2 依据这一接口边界实现。官方参考：`https://developers.openai.com/api/reference/cli/resources/responses/methods/create`

本次没有真实发送外部 API 请求，因为工作环境没有用户授权的 API Key。已经通过伪响应测试验证请求 Schema、解析路径和未知证据 ID 拒绝逻辑。真实网络调用仍需用户选择模型并承担相应隐私与费用。

## 8. 现在怎样运行 V0.2

```powershell
python -m ai_memory init
python -m ai_memory import examples/learning-project.json
python -m ai_memory compile
python -m ai_memory topics
python -m ai_memory topic 学习方法
python -m ai_memory knowledge
python -m ai_memory review 学习方法 approve --note "已核对原文"
python -m ai_memory serve
```

如果选择外部模型：

```powershell
$env:OPENAI_API_KEY="你的密钥"
python -m ai_memory compile --extractor openai --model "你明确选择的模型ID"
```

不要把真实密钥写进 `.env.example`、README、测试或聊天导出文件。项目已忽略 `.env` 与本地数据库，但在上传 GitHub 前仍应检查暂存文件。

## 9. V0.2 新增接口

| 请求 | 用途 |
|---|---|
| `GET /v0/topics` | 查看主题及其证据、对话、项目数量 |
| `GET /v0/topics/{id或中文slug}` | 查看一个主题的完整证据 |
| `GET /v0/knowledge-documents` | 查看文件路径、审核状态和当前修订 |
| `GET /v0/knowledge-documents/{id}/revisions` | 查看某文件的修订历史 |

V0.1 项目、问题、搜索和原消息接口继续保留。HTTP 服务仍然只读，没有鉴权，不能直接部署到公网。编译与审核必须在本地命令行完成。

## 10. 验证结果与发现的问题

9 项测试全部通过。测试覆盖：V0.1 导入与搜索回归；ChatGPT 父子消息映射；跨对话主题文件；来源未变化时跳过；强制编译不制造重复修订；新来源产生新修订并重置审核；OpenAI JSON Schema 请求；模型伪造证据 ID 被拒绝；中文主题 URL 正确解码。

真实接口联调结果为：健康状态 `ok`、版本 `0.2.0`、主题 5 个、知识文件 5 个、“学习方法”证据 6 条、当前修订 1 个。JSON Schema 文件也完成了解析检查，代码中没有发现类似真实 API Key 的字符串。

联调过程中实际发现并修复了中文主题 URL 未解码的问题。这说明测试和真实运行都很重要：如果只看代码文件是否存在，这种问题很可能到 UI 阶段才暴露。

## 12. 上传 GitHub 前必须注意

第一，不要提交真实聊天导出、SQLite 数据库、API Key 或包含个人信息的截图。第二，保留 LICENSE、SECURITY、CONTRIBUTING、CHANGELOG 和 CI。第三，把“默认离线”和“选择外部模型才上传内容”写在 README 显眼位置。第四，明确 V0.2 是 Alpha，禁止将无鉴权 API 暴露公网。第五，使用合成数据制作演示 GIF。第六，为每个连接器说明数据来源与用户授权前提。

发布时建议把产品名逐渐调整为 `AI Project Memory` 或 `LLM Project Memory`，同时在说明中保留 GPT-SaaS 是早期目录名。这样更符合“所有 AI 项目都能使用”的定位，也避免用户误以为只支持 ChatGPT。

## 13. 如果由你学习，V0.2 应掌握什么

| 学习主题 | 你要回答的问题 | 动手练习 |
|---|---|---|
| 多对多关系 | 为什么一句话可以进入多个主题 | 查询 `topic_evidence` 并画关系图 |
| 内容哈希 | 为什么重复编译不创建版本 | 连续运行两次 compile 对比结果 |
| 修订历史 | 新知识为什么要重置审核 | 批准文件、导入新对话、再次编译 |
| 接口抽象 | 为什么模型可以替换 | 对比 heuristic 与 openai 提取器 |
| JSON Schema | 怎样约束模型输出 | 故意返回错误证据 ID 并观察拒绝 |
| 隐私边界 | 什么时候数据会离开电脑 | 查找代码中唯一的网络请求位置 |

最推荐的练习是：在示例中新增第三条对话，内容同时涉及“英语复习”和“学习计划”，重新编译，然后观察一句话是否进入多个主题，以及哪些文件修订号发生变化。

## 14. V0.3 最合理的方向

V0.3 应优先解决可信度与可用性，而不是马上堆更多 AI。建议顺序：来源删除与知识失效标记；相似主题合并和冲突检测；一组可量化的抽取评测；最小本地 Web UI；导入预览与权限提示；最后再加入更多真实平台连接器。

最小 UI 可以只有四块：左侧项目与知识树，中间知识文件，右侧证据抽屉，顶部“待审核”队列。用户点击任何观点，都能看到它来自哪个项目、哪条对话和哪句话。这会第一次把 V0.2 的工程价值完整展示给普通用户。

## 15. 今晚的完成边界

V0.2 已达到本轮完成标准：数据可以从原始句子被编译成跨对话主题文件；核心内容与问题、AI 扩展分离；证据可回溯；相同内容不制造重复版本；新内容触发重新审核；本地接口可以读取主题和修订；项目具备基本开源发布文件。

现在最好的动作不是继续熬夜堆 V0.3，而是保存成果、阅读 `output/knowledge/学习方法/README.md`，确认它确实符合你的想法，然后休息。下一轮再从真实使用反馈决定 UI 和冲突检测的优先级。
