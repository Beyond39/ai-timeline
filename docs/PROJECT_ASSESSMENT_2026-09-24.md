## 怎么打开

1. Windows 中打开项目目录 `D:\mytools\GPT-SaaS`，双击 **Open Project Memory.cmd**。窗口保持打开，浏览器会自动访问 `http://127.0.0.1:8765`；若没有自动弹出，自己打开该地址。关闭命令窗口即可停机。
2. 或在项目根目录 PowerShell 输入 `python -m ai_memory launch`。若 Python 命令不可用，需先安装 Python 3.11 或更新版本并确保它在 PATH 中。
3. 先点 **选择文件** 导入 `examples/v042-semantic-demo.json` 体验流程，或点 **粘贴对话** 放入自己的原文。预览确认后再导入。Offline 模式可立即使用。
4. 想验证真正的 Semantic Compile，需要在**启动服务前的同一个 PowerShell 窗口**设置 `OPENAI_API_KEY` 与 `AI_MEMORY_MODEL`，再启动并在网页选择 Semantic。不要把 Key 提交到仓库。命令示例见 `docs/V0.4.2_FIRST_SEMANTIC_MEMORY.md`。

## 下一阶段：AI 做什么，用户做什么

**AI 可以独立完成的工作**：修复测试发现的 bug；改进分段和主题匹配；汇总反馈表，按错误频率生成待办；补长对话、失败重试、缓存和 UI 回归测试；完善本地启动、备份和说明。只有拿到真实错误样本后，语义优化才有明确方向。

**用户最少需要做的工作**：挑选并授权 3–5 段能代表同一项目的真实对话，必要时脱敏；如选择 OpenAI 模式，在本机配置密钥和有权限的模型；查看系统抽取的至少 20 个片段，标出哪些主题、证据和摘要符合自己的理解。这些判断无法由合成测试代替。之后 AI 可以继续分析和修复，不需要用户写代码。

建议把 **V0.4.3 定义为真实试用与质量修复**，不再增加大模块。合格门槛可先用：导入后原文完整；至少 20 个片段有人评价；无证据断链；错误主题可在界面纠正且刷新/重编译后保持；对高频错误完成一轮修复。主题准确率与摘要支持率的数值门槛，应在首轮真实样本后由用户根据用途确定，现阶段不虚构百分比。

## 精力估算

以下是基于当前代码范围的粗略规划，不是承诺工期或 API 费用。

| 目标 | 用户投入 | AI/开发工作量 | 主要不确定性 |
| --- | --- | --- | --- |
| 第一次真实试用 | 约 30–90 分钟：选/脱敏对话、配置 Key、抽查 20 片段 | 约半天到 2 天：处理试用中显露的启动/格式问题 | 数据格式、模型权限和网络 |
| 好用的个人本地工具 | 后续每轮约 15–30 分钟反馈，通常 2–4 轮 | 约 1–3 周的集中迭代 | 真实对话跨题复杂度、用户对主题树的期望 |
| 可给陌生人稳定使用 | 需持续找用户并验收 | 通常还需数周到数月 | 安装、备份恢复、隐私、安全、兼容性与支持成本 |

先不要把“好用的个人工具”和“公开产品”混为一个目标。现在最省用户精力的路径是：AI 负责实现与问题归因，用户只做一次短而真实的试用。真实语义质量尚无法从 39 项自动测试中推出。

## 可立即执行的顺序

1. 双击启动；先用合成示例熟悉按钮，不需要 API Key。
2. 导入 3–5 段同一真实项目的对话，核对原文和证据。
3. 配置模型并 Semantic Compile；抽查至少 20 片段。
4. 把反馈留在应用内，交给 AI 做错误统计与 V0.4.3 修复。
